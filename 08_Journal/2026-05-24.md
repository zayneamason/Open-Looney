## SPEC-007 post-implementation amendments

Two deferred carry-forward items from yesterday's reader v0.3.2 work
(2026-05-23 entries #6 and #7) landed today as docs-only amendments to
SPEC-007. Both followed the same post-implementation-clarification
pattern established by the bare-name fix bullet at
`SPEC-007_cartridge-sketches.md:354` on 2026-05-23 — keep the spec in
`01_Specs/implemented/`, append sub-bullets to Implementation notes,
bump `Last updated`, no status-line transition. No engine, reader, or
cartridge change.

- **What changed.**
  - **SPEC-007 § 7.1.2 (lines ~89–91).** New "Integer-width discipline
    (reimplementer hazard)" paragraph inserted between the existing
    "Other hash families MAY be added…" sentence and the `seed`
    paragraph. ~10 lines. Documents that the Kirsch–Mitzenmacher
    formula `(h1 + i*h2) mod num_bits` requires uint128-or-wider
    arithmetic in fixed-width languages; uint64 silently overflows
    when `h2` has its high bit set (~half of all hash values),
    producing bit indices that diverge from a correctly-arithmetic'd
    Python implementation and violating the "false = definitely not"
    contract from § 7.3.1. Cross-references § 7.3.1 step 4 (the
    existing OOB-guard) and journal entry #6 (the case that motivated
    the clarification).
  - **SPEC-007 § 7.4 (sizing table at lines ~182–192).** Replaced the
    four data rows + total + storage-claim paragraph with post-rebuild
    values against the 2026-05-23 Meditations cartridge (engine
    `24c19c2`): `extraction_ulid` n=1,106 → 2,758; `node_ulid`
    n=3,813 → 3,813 (deterministic); `entity_surface` n=532 → 912
    (post-bare-name); `fts_term` n=~4,500 → 6,843. Total storage
    12 KiB → 17 KiB; overhead 0.5% → 0.37%; cartridge size 2.5 MiB →
    4.59 MiB. Cross-reference at the top of § 7.4 swung from the

    `entity_surface`), with the load-bearing invariant called out

- **Why each amendment now.**
  - **§ 7.1.2 integer-width clarification.** The u64-overflow bug is
    the kind of cross-language hazard that's only obvious once you
    hit it — and the existing spec gave no signal to a reimplementer
    in Rust, Swift, Go, C++, or JS that the Kirsch–Mitzenmacher inner
    loop needed wider-than-uint64 arithmetic. Pinning the lesson into
    the spec stops the next reimplementer from re-paying the same
    diagnosis cost (~3 hours of bisecting bit-index divergence
    between Rust and Python yesterday). The pinned regression test
    in `shelf.rs:354-372` is the runtime artifact; this paragraph is
    the prose-level artifact for anyone reading the spec without the
    Rust source open.
  - **§ 7.4 sizing re-baseline.** The original § 7.4 table was authored
    against pre-NFKC, pre-bare-name vocabulary counts and a v0.2
    cartridge size. After the SPEC-007 § 7.1.1 normalization landed,
    after the bare-name fix landed, and after the cartridge rebuild
    on 2026-05-23, every number in the table was stale. Leaving the
    stale table in place would have invited future readers to derive
    wrong storage estimates or assume the counts were normative
    targets rather than observations. Re-baselining now keeps the
    spec honest while the rebuild details are still fresh in the
    journal.

## M-01 resolved — PDF parser merges multi-line title blocks

Third entry today. M-01 has been on the carry-forward queue since the
2026-05-22 v0.2 audit (`04_Audits/AUDIT_2026-05-22_meditations-v02.md:62-70`)
and was renamed to a v0.3 carry-forward in the v0.3 audit. Closed today
with an engine-side parser fix + cartridge rebuild + commit. Same-day
plan-investigate-fix-verify-commit loop.

- **Symptom.** `meta.title = "The meditations of"` in the Meditations
  cartridge (18 chars, semantically truncated mid-phrase, ends in
  function word "of"). The v0.2 title blocklist
  (`builder.py:33-49`: length<3, leading-glyph, no alphanumerics,
  `{untitled, document, document1}`) doesn't catch this because the
  string passes every check — it's truncation at a legitimate word
  boundary, not parser garbage.

- **Root cause** (confirmed via Phase 1 Explore agent + direct read
  of `pdf.py`). The Meditations title page lays the title across two
  visually-adjacent lines at the same 33.12pt font:
  ```
   0. [ 5.04pt] "Marcus Aurelius' Meditations - tr. Casaubon..."  ← below median, not heading
   1. [ 8.40pt] "Page 1 of 128"                                   ← below median, not heading
   2. [33.12pt] "The meditations of"                              ← heading (became section #1)
   3. [33.12pt] "Marcus Aurelius Antoninus"                       ← heading (became section #2)
   4. [12.00pt] "Originally translated by Meric Casaubon"         ← body
  ```
  The PDF parser at `pdf.py:222-226` emitted each heading-classified
  line as a separate section node. The builder at `builder.py:219-224`
  then walks nodes and picks the FIRST section with content as
  `raw_title` — which is block 2 alone. The two-line title was
  fragmented across two sections.

- **Why parser-layer not blocklist-layer.** The audit's recommended
  fix was a "trailing-function-word or minimum-word-count heuristic"
  in the blocklist, or "move title selection further into the
  document body." Both are symptom-level patches. Considered and
  rejected:
  - A function-word heuristic in `_validate_title` would conflate
    parser-garbage detection (the blocklist's job) with semantic
    truncation detection (a different concern), and would false-
    positive on legitimate titles like "Attention Is All You Need"
    (ends in "Need", not a function word, but the heuristic would
    have to be carefully curated).
  - Picking a later section as the title would lose information
    when the document has no clear "second heading" structure.

  The parser-layer fix solves the root cause: the two same-font
  lines ARE one logical heading, the parser should emit them as
  one section node, then the builder's first-section-with-content
  logic naturally produces the right title.

- **What changed in the engine (commit `cd7be64`).**
  - `src/luna/cartridge/parsers/pdf.py` (+27 / -2 LOC) — extended
    the heading branch inside `_parse_text_page`'s grouping loop
    (lines 222-226 in the prior version). When the first
    heading-classified line is consumed, peek ahead and merge
    consecutive `text_groups` that satisfy three conditions:
    (1) also `is_heading=True`, (2) font size within 0.5pt of the
    starting heading's font, (3) vertical gap to previous heading
    line ≤ 1 line-height of the next line. Merged lines become a
    single section node with space-joined text. Different font
    sizes (e.g. subtitle in a smaller size) or a larger vertical
    gap break the merge, so structurally-distinct headings stay
    separate.
  - `tests/test_cartridge_pdf_parser.py` (NEW, ~115 LOC; 3 tests)
    — builds synthetic 1-page PDFs via `fitz.insert_text` at
    known positions and font sizes; asserts the first
    section-with-content equals the expected merged title.
    Tests cover: positive merge case (two 33pt lines close
    together → merged), negative-by-font-size (30pt + 20pt → not
    merged), negative-by-gap (two 30pt lines 150pt apart → not
    merged).
