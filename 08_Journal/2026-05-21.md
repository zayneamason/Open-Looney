# 2026-05-21 — status sweep: v0.2 has shipped; repo state lags reality

**Summary:** The four accepted v0.2 specs (SPEC-006, SPEC-001, SPEC-002, SPEC-003) were
implemented Phases 1–5 in the engine repo over 2026-05-12 through Phase 5 closeout. The
research repo's framing still treats them as "accepted, awaiting implementation." Repo
hygiene is the cheapest action item; the substantive next move is the governance arc
(SPEC-004 / SPEC-005).

  `HANDOFF_NEXUS_LUN_V02_PHASE5_MIGRATION_CLOSEOUT.md` rev 2.

## Format-spec gap

`03_Format_Spec/` has only `LUN-FORMAT_v0.1.md`. The v0.1 doc carries "v0.2 changes"
inline annotations, but per the README's naming convention
(`LUN-FORMAT_v0.X.md` per version) v0.2 deserves its own canonical doc now that it's
the shipping format. v0.1 stays as a historical reference.

The v0.2 doc would consolidate the SPEC-006/001/002/003 surface into one place — the
full v0.2 schema (with ULID columns, anchor_status, raw signals, no `confidence`),
the pragma contract (`application_id`, `user_version`, journal_mode), the meta key
set (`format_version`, `cartridge_kind`, `source_filename`, `logprob_base`,
`logprob_attribution`, `deprecated_columns`), and the v0.2 validation checklist.
Most of this material already exists; it just needs to be lifted out of the specs and
arranged as a reference document rather than a change log.

## Carried-forward Phase 5 deferreds

These are tracked in SPEC-001 / SPEC-002 / SPEC-003 implementation notes but worth
naming in one place so they don't get lost:

1. **Lansing 9.5%-baseline measurement undefined.** The Phase 5 rebuild went through
   Path B (no source PDF available); reconstructed markdown has no `#` headings, so the
   parser produced 1 section, extractor truncated at 8000 chars (`extractor.py:167`),
   Haiku returned 1 summary + 15 entities + 0 claims. Cartridge is structurally valid
   but the headline `claim_match_failed / (claim_anchored + claim_match_failed)` ratio
   is `0/0`. Resolution path: either recover the original PDF (Path A), or add a
   chapter-detection pre-process that injects `#` markers into the reconstruction
   before build. The 9.5% number from the 2026-04-21 audit is currently unverified
   against any v0.2 build.
2. **`\x0c` form-feed artifacts in cartridge text.** PDF page-break characters survive
   the markdown reconstruction and end up in `doc_nodes.content`. Parser tolerates
   them but they're visible on inspection. Strip as part of any future chapter-splitting
   pre-process.
3. **v0.3 territory: drop integer `extractions.id`.** SPEC-002's D5 staged this as the
   removal phase. ULID is the operational PK; the integer column is now bookkeeping.
   `meta.deprecated_columns = 'doc_nodes.id,extractions.id'` already flags this in v0.2
   builds.
4. **Full SPEC-001 orphan semantic classification.** Phase 5 migration applies the
   spec-documented `migration_unclassified` fallback uniformly. The real
   synthesis/filtered detection (multi-lineage similarity + section-type heuristics)
   was deferred to "likely SPEC-004 consumer territory." Worth deciding whether that's
   actually SPEC-004's job or a separate spec.
5. **Backend logprob exposure.** `HaikuResult.usage` fields aren't surfaced yet;
   current paired-NULL satisfies the SPEC-003 contract but the response-level signal
   isn't being captured for every cartridge build. v0.3 backend-side improvement.
6. **`magic.txt` upstream registration.** Both `LUNC` (`0x4C554E43`) and `LUNM`
   (`0x4C554E4D`) values are in use; neither is registered with the SQLite project.
   Courtesy submission, not load-bearing.

## Governance arc — what's next

The whole point of v0.2 was to lay the foundation for the governance work. v0.2 is
foundational, not governance. Two specs are referenced repeatedly across the accepted
specs as the natural consumers:

- **SPEC-004 (multi-axis imprint weights, planned).** Composes raw signals from
  SPEC-001 (`anchor_status`, `anchor_method`) and SPEC-003 (`llm_logprob_sum`,
  `extraction_method`) into separable axes — authority, contestation, temporal,
  resonance. SPEC-003 was explicit that this is its primary downstream consumer.
  Likely also the home for the full orphan semantic classification deferred in
  item 4 above.
- **SPEC-005 (annotation events / append-only ledger, planned).** Adds the ledger,
  annotation events with provenance, and the `claim_sources.event_id` consumer
  (SPEC-001 left that column NULL and forward-referenced SPEC-005). The SQLite
  research already did the heavy lifting on the hash-chain pattern
  (`05_Reference/SQLite_Research.md` Topic 3); the spec is mostly write-up at this
  point.

Neither has a draft yet. Both are referenced as `planned` in every accepted spec's
governance section. Drafting either one would unblock real progress; my recommendation
is SPEC-005 first because (a) the research is already done, (b) it doesn't have any
remaining design questions of its own (multi-axis composition does), and (c) SPEC-001
left forward references into it that should be resolved before SPEC-004 lands.
