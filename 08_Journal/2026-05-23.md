- **Design decisions taken before editing (Ahab via AskUserQuestion).**
  All four matched the spec-author recommendations:
  1. **Populate mode: always populate during build.** Sketches are cheap
     (~milliseconds for Meditations) and the opt-out is "build with an
     older builder version." Matches the always-validate-ledger pattern.
  2. **Fsck integration: new `--sketches` flag; default unchanged.**
     Parallel to `--ledger` / `--payloads`; default fsck stays O(1) fast.
  3. **No migration for existing v0.3 cartridges.** Existing cartridges
     remain valid sketch-less; rebuild to gain sketches. Per SPEC-007
     § 7.5 graceful-absence handling.
  4. **Promote SPEC-007 → `implemented/` in same session.** Engine slice
     fresh; promotion is mechanical.

- **Engine change surface (9 files; ~810 LOC net).**
  - `pyproject.toml` — added `"mmh3>=4.0.0"` to dependencies. `mmh3` is
    the canonical Python MurmurHash3 binding; `mmh3.hash128(item, seed,
    signed=False, x64arch=True)` returns the 128-bit digest spec § 7.1.2
    requires.

  bit indices for `("virtue", seed=0, k=7, m=65592)` are
  `[54278, 48879, 43480, 38081, 32682, 27283, 21884]` and every
  corresponding bit is set in the loaded sketch).

- **Diagnosis path.** Two-step. First a Python re-verification
  confirmed the engine side was correct (h1=2065860924000221294,
  h2=6582964320913773025, indices as above, all 7 bits set). Then
  a temporary `06_Prototypes/ReaderPrototype/src-tauri/src/parity_check.rs`
  (mod-gated `#[cfg(test)]`) hardcoded those Python reference
  values and asserted Rust matched. `split_hash` matched
  (h1 + h2 identical). The first three bit indices matched
  (54278, 48879, 43480). The fourth diverged: Python 38081, Rust
  42385. Diffs grew from there. Root cause located in the
  Kirsch–Mitzenmacher inner loop.

- **The bug.** `bit_indices` at
  `06_Prototypes/ReaderPrototype/src-tauri/src/shelf.rs:119-126`
  did the math in u64:

  ```rust
  h1.wrapping_add(i.wrapping_mul(h2)) % m
  ```

  For any `i ≥ 1` where h2 has its high bit set (~half of all
  hash values), `i * h2` overflows u64. Rust's `wrapping_mul`
  returns `(i * h2) mod 2^64`, which is NOT the same as the
  mathematical `(i * h2) mod m` when reduced. Python uses
  arbitrary-precision ints; the same formula `(h1 + i*h2) % m`
  produces the correct value because no intermediate truncation
  happens. For `m = 65592` and h2 = 6582964320913773025
  (high bit set), divergence begins at `i = 3` exactly.
  This violates SPEC-007 § 7.3.1 — `sketch_contains` returning
  `false` is supposed to mean "definitely not in cartridge."
  The buggy bit_indices flipped some real-positives into
  false-negatives, breaking the consumer contract.

- **The fix.** Promote to u128 before the multiply/add.
  i is bounded by `MAX_NUM_HASHES = 32` (5 bits), h2 fits in
  u64 (64 bits), so `i * h2` fits comfortably in 2^69 « 2^128
  and the addition is also safe. Single-function change:

  ```rust
  fn bit_indices(item: &[u8], seed: u32, num_hashes: i64, num_bits: i64) -> Vec<u64> {
      let (h1, h2) = split_hash(item, seed);
      let h1_128 = h1 as u128;
      let h2_128 = h2 as u128;
      let m_128 = num_bits as u128;
      (0..num_hashes as u128)
          .map(|i| ((h1_128 + i * h2_128) % m_128) as u64)
          .collect()
  }
  ```

  Doc-comment above the function explains the bug history for
  future maintainers.

- **Why existing tests missed it.** Three pre-fix cargo tests
  touched the primitive but didn't catch the bug:
  - `bit_indices_in_range` at `shelf.rs:343` only asserts the
    indices are within bounds — silent on whether they're the
    right indices.
  - `sketch_contains_no_false_negatives` at `shelf.rs:379` builds
    a sketch by calling `bit_indices` to compute the bits to set,
    then queries by calling `bit_indices` to compute the bits to
    check. Same buggy primitive on both sides — the bug is
    symmetric, so the test passed.
  - `open_shelf_cartridge_with_sketches` at `shelf.rs:447` builds
    a v0.3 cartridge by calling Rust's `bit_indices` to populate
    the fixture sketch, then reads it via Rust's `sketch_contains`.
    Same problem: self-consistency, not external-reference parity.
  The general trap is well-known: when "build" and "verify" share
  a primitive, the test asserts only the primitive is consistent
  with itself, not that it matches the spec or any other
  implementation. The fix is to pin at least one test against an
  external reference.
