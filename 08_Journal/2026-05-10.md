# 2026-05-10 — application_id approach

**Decision:** Two distinct `application_id` values across the `.lun` family.

- Cartridge files (portable knowledge): `0x4C554E43` ('LUNC' big-endian ASCII)
- Runtime matrix files: `0x4C554E4D` ('LUNM' big-endian ASCII)

Set once at file creation. Never changes for the lifetime of a file.

## Context

The codex deep dive on 2026-05-10 (`Docs/Reports/REPORT_LUN_FILE_FORMAT_DEEP_STUDY_2026-05-10.md`) surfaced that `.lun` is now overloaded. `data/user/memory_matrix.lun` is the runtime substrate — its tables are `memory_nodes`, `graph_edges`, `conversation_turns`, `ih_events`, `nexus_nodes`, `nexus_edges`. Cartridge `.lun` files (e.g. `PRIESTS_AND_PROGRAMMERS_Lansing.lun`) carry `meta`, `doc_nodes`, `extractions`, `claim_sources`, `embeddings`, `nodes_fts`. Same extension, same SQLite, distinct schemas.

This research project (`Code for .lun Development`) was originally framed around cartridges only. The overlap means the format spec needs to scope itself explicitly, and an external observer needs a way to tell the two families apart without opening the schema.

## Reasoning

Two values rather than one. Three reasons:

1. **Fossil precedent (from `05_Reference/SQLite_Research.md`, Topic 1):** Fossil uses three distinct `application_id` values for repo / checkout / global config — same project, different file kinds, different IDs. SQLite's own authors set the convention.

2. **Audit principle:** Working principle #2 in the README is "every cartridge gets audited with generic SQLite tooling." A `file(1)` sniffer or audit script should be able to fast-reject "wrong kind of .lun" — that's what magic bytes are for. One value forces every tool to open the schema before it can know what it's looking at.

3. **"File is source of truth" principle:** Identity belongs in the file's bytes, not in a row of a meta table that could be missing, malformed, or stale. Distinguishing families via `meta.cartridge_kind` would be application-level discrimination — fragile in exactly the way the working principles are designed to avoid.

The cost of two values vs. one is one extra `magic.txt` row and one extra branch in any cross-family tool. Forward compat is fine: future flavors (chronicle, identity cartridge, etc.) get their own values when their schemas diverge enough to warrant it.

## Value selection

Both values verified absent from `magic.txt` per the research.

```
Cartridge family:  0x4C554E43 = 'L' 'U' 'N' 'C'  (Luna Cartridge)
Matrix family:     0x4C554E4D = 'L' 'U' 'N' 'M'  (Luna Matrix)
```

Both follow the convention of ASCII-encoding the project name. The 4th character distinguishes purpose. Cleanly memorable.

## Implementation pattern

At cartridge creation (`src/luna/cartridge/builder.py`):

```sql
PRAGMA application_id = 0x4C554E43;
PRAGMA user_version = 1;  -- v0.1 baseline
INSERT INTO meta (key, value) VALUES ('format_version', '0.1');
INSERT INTO meta (key, value) VALUES ('cartridge_kind', 'knowledge');  -- subtype within family
```

At runtime matrix initialization (`src/luna/substrate/database.py`):

```sql
PRAGMA application_id = 0x4C554E4D;
PRAGMA user_version = 1;
```

`user_version` increments per family on each migration. The two families don't share a version trajectory — cartridges might be at v0.2 while matrix is at v0.4 or vice versa. Both are tracked redundantly: `PRAGMA user_version` for fast machine inspection, `meta.format_version` for human inspection inside the schema.

## What cascades

- `03_Format_Spec/LUN-FORMAT_v0.1.md` retitled or scoped: it documents the **cartridge** family. Matrix gets its own spec when it earns one (not urgent).
- README updated to note the two-family approach and the application_id values.
- v0.2 hygiene bundle spec (forthcoming, SPEC-006 candidate) ships with both concrete values, the dual-tracking pattern, and the full pre-distribution pragma stack.
- Future `lun fsck` prototype gates on `application_id` first, refuses wrong-family files with a clear error before doing anything else.
- `magic.txt` upstream registration: submit both values to the SQLite project. Low priority — works fine without it, registration is a courtesy.

## Open / deferred

- **Matrix format spec.** Doesn't exist yet. Decision: defer until the matrix schema stabilizes (Nexus promotion bug fixed, `ih_*` tables settled, `conversation_turns` finalized). No urgency.
- **Subtypes within a family.** Knowledge cartridge vs. eventual identity cartridge, chronicle cartridge, etc. — captured in `meta.cartridge_kind` rather than separate `application_id` values, unless schemas diverge enough to need them. Re-evaluate as new types emerge.
- **Existing files.** `memory_matrix.lun` is already in use and almost certainly has `application_id = 0`. The hygiene bundle migration needs to set it correctly on first open after the v0.2 bump. Existing cartridges (just `PRIESTS_AND_PROGRAMMERS_Lansing.lun` at present) need a one-shot rewrite to set their `application_id`. Cheap because cartridges are built fresh each time.
